# BizBetter implementation status

## Financial integrity controls now in place

Production routes and screens use the local evidence repository in `lib/evidence`, not the legacy in-memory financial examples. Source records carry a business/environment boundary, source system and record IDs, import/sync ID, period, basis, currency units, timestamp, verification method, completeness, optional source payload and digest. Records and owner decisions persist under ignored `.bizbetter-data`; a hash-linked audit event is written for changes. The existing SQLite database was backed up before forward-only additive OAuth and sync-schema migrations; existing records were preserved, and SQLite integrity returned ok.

All legacy example datasets and analytical engines now live under `lib/demo` and `lib/demo-data.ts`. The normal routes cannot call those engines; the demo route clearly says “DEMO DATA — NOT REAL BUSINESS INFORMATION”. Database seeding requires an explicitly separate demo mode and demo database URL. CSV preview rejects guessed dates, missing amounts and unmapped categories. A separate normalized CSV import preserves owner-entered provenance and cannot claim provider verification.

Production analysis currently supports an accounting net-loss observation, a payment-fee review, negative direct job contribution, matched invoice-payment variance and definition-matched cross-source discrepancy. It shows the formula, source records, periods, quality, stated assumptions, confounders, challenges, confidence criteria, and evidence-based action steps. It does not label an observed cost as savings. Trends require eight complete consecutive matching months. Cross-series correlation requires at least twelve aligned months and is labeled a non-causal hypothesis. External benchmarks require publication, applicability, metric definition and URL provenance. The optional server-side OpenAI analyst now accepts a selected business workspace, sends a minimized evidence package, parses strict structured output, and validates citations and quantitative claims before returning results. It cannot write findings or Money Found stages. Provider availability still depends on a valid key and account access; a configured key alone does not establish a successful live response.

Money Found uses sequential potential → validated → implemented → realized transitions. Validation needs a named owner and reconciliation notes; implementation needs an accepted or modified decision and date; realized savings require the original cited invoice baseline, a same-currency/source/basis/entity/metric and equal-duration after record, an implementation boundary and written review of required confounders. Results preserve that the comparison does not prove causal attribution. Outcome patterns require at least three revalidated instances and remain descriptive.

## Verification

`npm run test:integrity` runs 18 integrity checks. `npm run test:connections` verifies evidence behavior and missing credentials. `npm run test:demo` runs legacy demo-engine fixture checks only; its invented figures are not production evidence. `npm run test:qbo-security` verifies token encryption round-trip, per-encryption nonce uniqueness, purpose binding and tamper rejection. `npm run build`, `node node_modules/typescript/bin/tsc --noEmit`, and `node node_modules/prisma/build/index.js validate` completed successfully. The local app is available at `http://127.0.0.1:3000`.

## Remaining work and limits

QuickBooks Online now has an OAuth 2.0 authorization-code scaffold: sandbox is the default; state is single-use and browser-bound; access and refresh tokens are encrypted with AES-256-GCM using a separately configured 32-byte key; refresh-token rotation is persisted; revocation clears local tokens; and company identity is checked before storing the connection. Only the read-only accounting scope is requested. The older manual-token QBO sync path is disabled. Intuit credentials were not configured, so no sandbox authorization or live provider request has been verified. Full 24-month ingestion, source-entity synchronization, durable background jobs, and scheduler are still pending. Stripe retrieval is capped at 10,000 transactions and reports partial coverage when that cap is reached. The other catalog providers remain explicitly unimplemented; some need partner approval, OAuth setup or plan access.

The evidence store is local single-user persistence, not hosted multi-tenant storage. Normalized evidence JSON is not encrypted at rest; QBO OAuth tokens are encrypted in SQLite. There is no login, deployment hardening, provider webhook worker or durable scheduled sync. Treat the hash-linked audit as tamper-evident application history, not immutable third-party attestation. Protect the Windows account and backups.

The analytical catalog does not yet detect underpricing, unpaid receivables, payroll/overtime, callbacks, technician/crew utilization, vendor price drift, ad CAC/attribution, customer/service/geographic contribution, seasonality, anomalies or cash-flow forecasts. Those require more provider adapters, careful normalized records, sample sufficiency rules, and separate validation. Current recovery guides explain the next checks; they do not claim a verified root cause or promise recovery.

Prisma migration status is up to date. The pre-change SQLite database backup is stored outside the project under the Windows temporary directory; it must be retained until the operator confirms the migrated application behaves as intended. Existing database models with hardcoded impact fields remain outside production calculations until migrated to store evidence references and currency units.
